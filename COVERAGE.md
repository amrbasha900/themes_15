### The master switch disabled the theme on every existing site

Reported from a live bench: the Desk rendered as stock Frappe — black primary
buttons, native inputs, native sidebar. That was not a styling problem, it was
the theme not loading at all, and the cause was the master switch added one
commit earlier.

`enable_theme` was read as
`cint(settings.get("enable_theme")) if settings.get("enable_theme") is not None else 1`.
That guard can never fire. `BaseDocument._fix_numeric_types`
(`frappe/model/base_document.py:723`) runs `cint()` over **every** Check field
when a Single loads, so an unset Check reads back as `0`, never `None`. The new
field had no row in `tabSingles` on any existing site, so it resolved to `0`,
`data-tm-enabled` was written as `off`, and the guard stripped all 713 rules
including the Frappe variable bridge.

The same latent bug applied to the four area flags on any site where
`after_install` had not populated them.

Flags are now read with `frappe.db.get_single_value`, where `NULL` still means
unset, and `after_migrate` writes an explicit value so the checkbox in Theme
Settings matches reality. `tests/flags.test.py` reproduces Frappe's Check
coercion faithfully and fails against the old code with exactly the reported
symptom (`flags.theme == 0`).

**Diagnosing this class of failure:** `bench --site <site> execute
themate.diagnostics.run` walks every layer that must hold for a single pixel to
change — app installed, assets built, hooks registered, flags on, boot payload
readable — and names the fix for whichever one is broken.

### Three regressions found in review, after the first rebuild

All three were reproduced in a browser before being fixed, and all three were
**interaction** bugs — CSS against JS, or bootstrap against the picker. The
original suites tested each layer alone, which is precisely why they passed. The
new `tests/integration.test.js` runs the compiled stylesheet, the palette
module, bootstrap and the theme switcher **together**, and pins each regression
by name.

| Regression | Was | Now |
| --- | --- | --- |
| A saved Dark choice reverted to Light on reload | the site default always outranked the user's choice | `User.desk_theme` is the single store; the default speaks only when the user never chose |
| Brand colours overwrote dark mode | inline styles on `<html>` beat `[data-theme="dark"]`; `--tm-brand-500` painted `#1677ff` instead of `#1668dc` | mode-scoped CSS rules, generated by a port of Ant's own algorithm that reproduces both frozen ramps exactly; nothing emitted at all for the default brand |
| The picker showed a different colour than the page | two resolvers disagreeing on localStorage vs. configured value | one shared `effectiveAccent()` |

Two earlier bugs were found the same way, by tests rather than by reading:

1. **Disabled buttons stayed accent-coloured.** `.btn[disabled]` and
   `.btn.btn-primary` have identical specificity (0,2,0), so the variant won on
   source order. Fixed by moving the disabled block after every variant — the
   cascade resolves it, no `!important`.
2. A theme-flip assertion appeared to fail because `.btn` transitions
   `background-color` over 100 ms, so a computed read at t=0 returns the
   interpolated start value. That one was a test defect, not a CSS defect, and
   is documented in `tests/README.md` so it is not mistaken for a bug again.

## Sidebar — the significant open item

*2026-09-16:* the trio is now imported by the hashed bundles (see FRAPPE_UI_MAP.md §6) —
as un-hashed `/assets` files they sat behind nginx's one-year cache and no fix reached a
browser without a hard reload. Also fixed: `--sidebar-width` was 248px inside `.modern-sidebar`
but 224px for `.main-section` (24px of every page sat under the sidebar); active-item resolution
now follows Frappe's breadcrumb workspace instead of the last-visited one; active state is a
tint + start bar, not a solid fill.

`hooks.py` loaded `modern_sidebar.css` (1635 lines), `modern_sidebar.js`
(635 lines) and `msidebar_override.js` (120 lines). Their intended replacements
(`js/sidebar/sidebar.js`, `js/sidebar/flyout.js`) were 1-line stubs and have been
removed rather than left as misleading placeholders.

The legacy trio is **kept on purpose**. It is the only working sidebar, and
replacing 755 lines of mount, routing and collapse behaviour without a browser
to exercise it would trade a working sidebar for an unverifiable one — the
opposite of what the brief asks for ("remove legacy includes only once its
replacement works").

What was done instead: `modern_sidebar.css`'s own `--sidebar-*` variables were
re-pointed at the shared `--tm-*` tokens **at their source**, so the sidebar
tracks the palette, density and radius and its width stays in step with the
layout offsets. There is one owner for sidebar appearance and no override war —
`layout/_sidebar.scss` deliberately does not style `.modern-sidebar`, because
`modern_sidebar.css` loads *after* the bundle and winning would have required
`!important`.

**To finish it**, on a real bench: build the v2 sidebar behind the existing
`data-tm-sidebar` flag, verify both side by side, then drop the legacy includes
from `hooks.py` in the same commit that ships the replacement.

## Known limitations, stated rather than hidden

1. **Rollback is master-level, not per-area — by necessity.** `Enable Theme` in
   Theme Settings turns the whole theme off: tokens, the Frappe variable bridge
   and every component rule, leaving stock Frappe. That is a genuine rollback
   and is asserted by 15 checks in `tests/integration.test.js`.

   Per-**area** rollback cannot restore colours, and this is a property of
   Frappe rather than a shortcut here: `--primary`, `--bg-color`,
   `--border-color` and the rest are defined on `:root` and consumed globally
   (`common/css_variables.scss`), so there is no way to hand the List View back
   its native palette while the Form keeps the themed one — they read the same
   variables. The per-area switches therefore remove an area's **structure**
   (padding, borders, heights) and leave the palette alone. Use the master
   switch to rule the theme in or out; use the area switches to narrow down
   *which* area's structural rules are involved.
2. **`:has()` is required** for the distinct selected-row background. It is
   unavailable in browsers older than ~2023; those users see hover styling on
   selected rows. Frappe offers no class to use instead.
3. **The Ant Design references are named, not captured.** No Ant Design page was
   opened or diffed. The contract in `DESIGN_CONTRACT.md` is the authority;
   §2 there lists the three reference screens still to be pinned.
4. **The Datavalue app was not fetched** — GitHub scope here is limited to
   `kimoamer/themate`. Its decisions are recorded in `FRAPPE_UI_MAP.md` §7 from
   the brief's own source trace, and flagged as unverified.
5. **`Theme Settings` name collision.** Both Themate and `datavalue_theme_15`
   define a Single DocType with that name and different schemas. Do not
   co-install without resolving ownership first.
6. **The DocType `brand_color` default changed** from `#3b6fec` to `#1677ff`.
   This affects **new installs only**; existing sites keep their stored value.
